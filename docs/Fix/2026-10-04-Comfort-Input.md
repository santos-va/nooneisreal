# Ізоляція бойового вводу від меню комфорту

**Статус:** завершено на `codex/comfort-settings-input`: `COMFORT_INPUT_CHECK checks=31 failures=0`, `make check-playable` — 19 сценаріїв / 0 провалів (включно з базовим `make check`), `make gates` — «БАТАРЕЯ ЗЕЛЕНА». Журнали `/workspace/nooneisreal-env/comfort/logs/{input,check-playable,gates}.log` прочитано в цій сесії після послідовних запусків T1; Godot 4.7.

Предмет: для всіх клавіатурних і геймпадних дій `InputRouter` відкритий UI не створює бойову дію, а утримання через закриття UI потребує повернення до нейтралі.

## Аудит і вибір

До зміни `_input` записував буфер раніше за обробку GUI, а `held`, `axis` і `move` читали фізичний `Input` напряму. Тому клавіша атаки під час роботи з меню або утриманий стік могли перейти в бій після паузи.

Розглянуто три варіанти: `_unhandled_input` (не усуває утриманий ввід), глобальне `Input.action_release` (підмінює стан пристрою), токени власників UI з нейтральним бар’єром (обрано). Збережено розкладку, напрям руху відносно суперника, шестикадровий буфер і віртуальний шлях CPU поза UI.

Перевірені погляди: клавіатурний гравець із затиснутою атакою; геймпад із відхиленим стіком; другий локальний гравець; вкладені налаштування поверх паузи; CPU та автоматичний тест; UI, який видалено зі сцени.

## Реалізація

`InputRouter.acquire_ui(owner)` та `release_ui(owner)` ідемпотентні для одного власника. Різні власники утримують незалежні токени; слабке посилання дозволяє прибрати токен видаленого вузла. Меню, пауза і панель комфорту мають окремих власників.

Поки існує токен, усі бойові запити нейтральні, історія вводу очищена. Після закриття натиснуті фізичні дії залишаються заблокованими до відпускання. Події відпускання обробляються без очікування фізичного тіку, тож нове натискання в тому самому тіку не губиться. Аналоговий стік використовує вже наявну мертву зону InputMap. Розкладка не переписується.

Перший запуск цільового тесту виявив справжню гонку: відпущений у UI тап лишав `Input.is_action_just_pressed` для першого фізичного тіку після закриття (19 перевірок, 1 провал). Додано окремий бар’єр спожитих UI-натискань: його знімає тільки нова дозволена подія натискання. Це не дає фізичному polling відновити вже очищений буфер; перевірку не послаблено.

## Геймпад у меню

Перевірка UI виявила, що вбудований `ui_accept` у фактичному InputMap мав лише Enter, Enter цифрової клавіатури та Space. За погодженим дорученням T1 додано тільки UI-прив’язки: A — прийняти, B — назад, D-pad — чотири напрямки. `device = -1` допускає обидва контролери. `ensure_ui_gamepad_bindings()` зберігає всі клавіатурні події, не додає повторних однакових прив’язок і не змінює жодної бойової дії. Нові твердження перевіряють повторну ініціалізацію, клавіатуру та подію другого контролера для кожної з шести UI-дій.

## Перевірка

Команда: `$GODOT_BIN --headless --path game -s "$PWD/tools/input/comfort_input_check.gd"`.
Умова: код 0 і `COMFORT_INPUT_CHECK ... failures=0`; на провалі виправити ізоляцію, не послаблювати перевірку. Окремо потрібні `make check` та `make gates`.

Тест надсилає справжні `InputEventKey`, `InputEventJoypadButton`, `InputEventJoypadMotion`: короткий тап і споживання буфера, вкладені/повторні токени, утриманий рух та атака через паузу, повторне натискання після відпускання, тап лише в UI, CPU поза UI, видалення власника, тотожність усіх мап дій до/після. Форми зламу: запис натискання крізь UI; відновлення утриманої дії без нейтралі; передчасне зняття вкладеного блокування. Ці твердження перевіряються окремо.
