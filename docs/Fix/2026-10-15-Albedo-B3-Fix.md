## Ціль: що означає «і світло, і тінь у палітрі»

У кожній формі Б екран = альбедо × множник смуги (лінійно за A). Тому:

- **світло → hex палітри** — однозначно;
- **тінь → hex палітри** (метрика таблиці A/B 2026-10-14) — вироджена ціль. Обидві смуги влучають у hex лише тоді, коли
  множник тіні = множнику світла, тобто тіні немає (або `key_gain` 0 і вся заливка — емісія). Пласке місто без тіні
  суперечить стайл-гайду («пласкі базові кольори, **одна тінь**»). Цю ціль я не калібрував;
- **тінь → тінь стайл-гайду** = hex × `#B07AA6` поканально на sRGB-числах, як у його ж прикладі з кров'ю (`#711126`).
  На неї й калібрую. Стайл-гайд і палітра не змінюються.

У таблицях нижче тінь подано до обох цілей: «до тіні стайл-гайду» (на неї калібровано) і «до hex» (як 2026-10-14).

## Калібрування (Forward+, за формулою)

Команда: `python3 -I tools/art/albedo_b3_calibrate.py --json B3/calib.json --tsv B3/calib.tsv` → rc 0, лог
`B3/logs/calibrate.log`. Усі входи скрипт читає з репозиторію (`CityMaterials.gd`, `city_surface.gdshader`, `CityWorld.gd`,
`CityInteriors.gd`, `CityBackdrop.gd`, `toon.gdshader`, `NpcAppearance.gd`, `SwordPresentation.gd`, `gear_surface.gdshader`)
і падає з rc 2, якщо щось не знайдено.

Формула — та сама, що в T3 і в `albedo_ab_table.py` (Forward+: uniform-и лінеаризовані на CPU, `LIGHT_COLOR` =
lin(колір) · енергія · π, рушій множить `DIFFUSE_LIGHT` і ambient на `ALBEDO` один раз, `EMISSION` додається лінійно;
тонмап Linear; пласкі кольори, одне сонце). A = lin(палітри), L = lin(сонця) · 0,95 = (0,950; 0,887; 0,826):

- `city_surface` Б3: світло `A·(f·FS + g) + A·L·k·KS`; тінь `A·(f·FS + g) + A·(b·(1−m) + m·lin(T))·L·k·KS`;
- герої Б3: `A·amb + A·sh·L·HG` (кожен рядок `DIFFUSE_LIGHT` × HG / π), sh = 1 на світлі, `mix(T, 1, 1 − ss')` у тіні
  (смуга a = 0), `Tc · CS` у тіні тканини й спорядження; amb = lin(0,66; 0,66; 0,79) · 0,40 = (0,157; 0,157; 0,235).

Мірило — медіана ΔE76 по 19 ключах палітри району, окремо світло й тінь. У `city_surface` смуги ділять f і k, тому
пошук мінімізує суму двох медіан (сітка 11 × 17 × 6 × 11, потім покоординатний спуск); у героїв HG мінімізує медіану
світла (тінь на нього не впливає), потім `ss'` / CS — медіану тіні. Палітри в героїв немає (атлас), тому ключі району —
тестові альбедо: у формі Б множник не залежить від кольору, тож вибір тестових кольорів майже не важить.

**Нові числа (PLACEHOLDER, художні, округлено до 0,001):**

| шейдер | число | А (зараз) | Б3 | медіана ΔE76, Forward+: А → Б3 |
|---|---|---|---|---|
| `city_surface` (район) | `key_gain` | 2,2 | **1,053** | світло 14,0 → **2,7** |
| | `painted_fill` | 0,16 | **0,028** | |

| `city_surface` (інтер'єри, `CityInteriors.gd:21-22`) | `painted_fill` / `key_gain` | 0,28 / 1,65 | 0,049 / 0,790 (те саме відношення 0,175 / 0,4786) | |
| `city_surface` (тло, `CityBackdrop.gd:27-28`) | `painted_fill` / `key_gain` | 0,2 / 1,35 | 0,035 / 0,646 | |

| `toon` (NPC, tint `b07aa6`) | `shadow_strength` | 0,45 | **1,000** | тінь 19,6 → **5,4** |

Що з цього видно:
- `city_surface` прийшов рівно до правила стайл-гайду: `mix(vec3(0), T, 1)` = T, тобто тінь = колір × `#B07AA6`;
  `painted_fill` майже зник (0,028), бо будь-яка заливка піднімає «підлогу» тіні, а зелений канал цілі — лише 0,195.
- `key_gain` 1,053 < 1 / 0,95 через тепле сонце: одним множником не можна зробити світло нейтральним у трьох каналах;
  залишок — теплий відтінок на світлі (медіана ΔE 2,7).
- Тінь героїв не доходить до цілі так близько, як у міста: ambient (0,157…0,235) додається всюди, а tint тіла героя
  синюватий (стайл-гайд: «зараз синій — замінити у фазі 2»), меча — сірий `514559`. Кольори tint я не чіпав.
- Кинута тінь на героях (`ATTENUATION` 0) — це лише `A·amb` в усіх варіантах; Б3 її не рухає.

## Підміна Б3 (у пам'яті)

`albedo_ab_capture.gd` будує Б3 з коду Б1 точними підстановками `b3_edits()`; кожна має знайтись рівно один раз, інакше
rc 1. Константи — `B3` в інструменті; `albedo_ab_table.py` перераховує їх `albedo_b3_calibrate.py` і падає (rc 1), якщо
в receipt інші. Диф Б1 → Б3 (`--dump-shaders`, `diff B3/dump/shaders/<f>.B1.gdshader <f>.B3.gdshader`):

```diff
# city_surface.gdshader
-	EMISSION = paint * (painted_fill + glow);
+	EMISSION = paint * (painted_fill * (0.028 / 0.16) + glow);
-	vec3 shaded = vec3(1.0) * mix(vec3(0.50), shadow_tint.rgb, 0.35);
-	DIFFUSE_LIGHT += mix(shaded, vec3(1.0), lit) * LIGHT_COLOR * key_gain / PI;
+	vec3 shaded = vec3(1.0) * mix(vec3(0.000), shadow_tint.rgb, 1.000);
+	DIFFUSE_LIGHT += mix(shaded, vec3(1.0), lit) * LIGHT_COLOR * key_gain * (1.053 / 2.20) / PI;
# toon.gdshader (sword_dissolve — те саме з 0.945, hero_garment — з 0.895)
-	float k = mix(1.0 - shadow_strength, 1.0, a);
+	float k = mix(1.0 - clamp(shadow_strength * (1.000 / 0.45), 0.0, 1.0), 1.0, a);
-	DIFFUSE_LIGHT += shade * LIGHT_COLOR * ATTENUATION;
+	DIFFUSE_LIGHT += shade * LIGHT_COLOR * ATTENUATION * 0.914 / PI;
-	DIFFUSE_LIGHT += vec3(1.0) * rim * rim_strength * LIGHT_COLOR * ATTENUATION * step(0.0, ndl);
+	DIFFUSE_LIGHT += vec3(1.0) * rim * rim_strength * LIGHT_COLOR * ATTENUATION * step(0.0, ndl) * 0.914 / PI;
# hero_garment.gdshader, тканина
-	vec3 cloth_shade = mix(vec3(1.0) * vec3(0.69,0.48,0.65) * 0.75, vec3(1.0), smoothstep(-0.08,0.08,ndl));
+	vec3 cloth_shade = mix(vec3(1.0) * vec3(0.69,0.48,0.65) * 0.355, vec3(1.0), smoothstep(-0.08,0.08,ndl));
# gear_surface.gdshader
-	vec3 shadow = vec3(1.0) * vec3(0.69,0.48,0.65) * 0.75;
+	vec3 shadow = vec3(1.0) * vec3(0.69,0.48,0.65) * 0.355;
-	DIFFUSE_LIGHT += (shaded + vec3(1.0) * edge * rim * step(0.0,ndl)) * LIGHT_COLOR * ATTENUATION;
+	DIFFUSE_LIGHT += (shaded + vec3(1.0) * edge * rim * step(0.0,ndl)) * LIGHT_COLOR * ATTENUATION * 0.914 / PI;
```

Чому множник, а не нове значення uniform-а: `CityInteriors` і `CityBackdrop` задають свої `painted_fill` / `key_gain`
явно, і нове значення за замовчуванням їх не зачепило б. Множник `(нове / старе)` зберігає відношення кожного набору до
району. Якщо Santos обере Б3, у продукті це будуть звичайні нові числа (таблиця вище), а не множник у шейдері.

## Результат: ΔE76

**Кадри — Compatibility / llvmpipe. Колонки «F+» — розрахунок для Forward+ (M3), не замір.** Медіана по ключах району,
пікселі Choko зважені й усереднені в лінійному світлі (`B3/py/md_b3.py B3/table`). Ціль: світло → hex палітри, тінь → hex ×
`#B07AA6`; у дужках — тінь до самого hex, як у таблиці 2026-10-14.

| смуга | А, Compat кадр «сонце» | Б3, Compat кадр «сонце» | А, F+ формула | Б3, F+ формула | А, кадр «як є» | Б3, кадр «як є» |
|---|---|---|---|---|---|---|
| світло (n 17) | 15,5 | **2,9** | 14,1 | **2,7** | 15,3 | 6,3 |
| тінь (n 18), до тіні стайл-гайду | 19,4 | **12,8** | 16,6 | **2,6** | 24,1 | 26,4 |
| тінь (n 18), до hex (метрика 2026-10-14) | (21,2) | (17,4) | (20,9) | (29,4) | (19,2) | (16,6) |

Для довідки Б1 у тій самій серії: світло 24,0 (кадр «сонце») / 21,1 (F+); тінь до hex 8,9 / 6,3 (2026-10-14:
24,1 / 21,1 і 8,9 / 6,3).

- **Світло** в Б3 влучає в палітру в обох рендерерах: 2,9 (кадр) і 2,7 (F+). Залишок — тепле сонце (одним множником
  нейтральним не зробити) і візерунок поверхні.
- **Тінь** у Б3 влучає в тінь стайл-гайду лише у Forward+ (2,6). У кадрі Compatibility — 12,8: там `shadow_tint` іде в
  `light()` сирим sRGB-числом (T3, кейс D), тобто множник тіні (0,69; 0,48; 0,65) замість лінійного (0,43; 0,20; 0,38).
  Тінь у кадрі світліша й сіріша, ніж буде на M3.
- **Модель Compatibility збігається з кадрами Б3** (серія «сонце»): медіана ΔE кадр ↔ модель 0,4 (світло) і 0,5 (тінь),
  максимум 10,5 — `warm_window`. Для А це 6,0 і 5,6 (по ключах); по рядках станцій А 5,1 / 5,4, Б1 4,9 / 5,5, Б3 0,5 /
  0,5. Чому А і Б1 розходяться з моделлю,
  а Б3 ні, я не з'ясував; перевірені гіпотези (`ALBEDO` у `light()` як sRGB-число; `EMISSION` без перетворення) дають ще
  більшу розбіжність — відкинуто.
- **Серія «як є» (з лампами крамниць)** у Б3 гірша, ніж «сонце»: тінь 26,4. Лампи в Compatibility світять на весь меш
  (знахідка [[2026-10-14-Albedo-AB-Fix]]: `light()` не множить на `ATTENUATION`), а в Б3 їхній внесок лінійний за кольором
  (в А — квадратичний), тому тіньові стіни біля крамниць рожевіють (`terracotta` тінь «як є»: А 43,1 → Б3 45,2). Це вада
  `light()` для omni, не частина Б3; на M3 (кластери Forward+) не перевірено.

## Для Santos — що зміниться на екрані в Б3 проти А

Простими словами, без формул. Опис — за розрахунком для твого Mac (Forward+); кадри з Linux це показують лише частково.

1. **Освітлені поверхні стануть кольорами зі стайл-гайду.** Зараз темні кольори на сонці темнішають майже до чорного
   (залізо, скло, сланець), а світлі жовтіють (штукатурка, кремова тканина). У Б3 кожен колір на сонці — той, що в палітрі.
   Похибка (ΔE) падає з 14 до 3.
2. **Тіні стануть бузковими, як велить стайл-гайд** («тінь = колір × `#B07AA6`»). Зараз тінь — сіро-бура й залежить від
   кольору: темні речі в тіні чорні, світлі — ледь темніші. У Б3 тінь однакова для всіх кольорів: помітно темніша за
   світло й виразно бузково-маджентова. Наприклад, штукатурка в тіні: зараз беж `#93785f` → у Б3 бузково-рожевий `#80525a`.
3. **Ризик — темні речі в тіні.** Тінь фарбованого чавуну, заліза, скла підходить близько до кольору контуру `#2B2230`:
   контур на темних речах у тіні читатиметься гірше. Для чавуну T6 вимагав «тінь ≥ 20 від лінії» — у Б3 це 9.
4. **Герої** на світлі лишаються майже такими, як зараз (без пересвіту Б1). Тінь на тілі трохи глибша; у мешканців —
   бузкова. Колір тіні в самих героїв синюватий (стайл-гайд давно каже замінити) — його Б3 не міняє.
5. **На твоєму M3 буде інакше, ніж на кадрах.** Кадри зняті на Linux у режимі Compatibility: там колір тіні підставляється
   «сирим», тож тіні на кадрах **світліші й сіріші**, ніж будуть у тебе. Ближче до правди — аркуш-зразки
   `2026-10-15-albedo-b3-swatches.jpg` (порахований для Mac), але й він — розрахунок, не знімок з M3. Справжню картинку
   покаже лише запуск на M3.
6. Біля ламп крамниць на Linux-кадрах Б3 тіні рожевіють — це окрема вада освітлення ламп, на Mac вона може бути меншою
   (не перевірено).

Вибір А / Б1 / Б3 — твій; у гру нічого не пішло.

## Негативні контроли інструмента

Предмет: для всіх поверхонь світу на п'яти шейдерах і кожної станції: кадр Б1 намальований кодом Б1, кадр Б3 — кодом Б3
з усіма підстановками, а кадр А2 побайтно дорівнює А.

Станція `plaster`, остаточна версія інструмента (`3dcf3771…b096`); лог `B3/logs/neg.log`, теки `B3/neg/<форма>/`.

| форма (`--break=`) | що ламає | результат |
|---|---|---|
| `nolight` | у `city_surface` немає `light()` | rc 1: `light(): replaced=0 left=-1`; і дві підстановки Б3 `matches 0 times`; таблиця rc 1 |
| `foreign` | одна міська поверхня на `Shader.duplicate()` | rc 1: перепис `start: 1 slots … (no path)` і те саме на станції; таблиця rc 0 (вона цього не бачить — як і 2026-10-14) |
| `stuck` | Б1-код `city_surface` = А | rc 1: `frame B1 is byte-identical to A` (на цій станції героя в кадрі немає); таблиця rc 1: `city pixels changed A->B1 only 0.0 %` |
| `leak` | найбільша міська геометрія не повертається після ID | rc 1: `frame A2 differs from A`; таблиця rc 1: `A2 differs from A in 14131 px` |
| `b3drift` (нова) | у коді `city_surface` рядок, який править Б3, переставлено (`glow + painted_fill`) | rc 1: `B3 edit matches 0 times (want 1): EMISSION = …`; таблиця rc 1: `b3 edits … matched [0, 1, 1]` |
| `stuck3` (нова) | Б3-код `city_surface` = Б1 | rc 1: `frame B3 is byte-identical to B1`; таблиця rc 1: `city pixels changed B1->B3 only 0.0 %` |

## MC7: `seen_y ≥ 4,0 м` (A5 T6)

Предмет: для всіх машин M на вуличних станціях S2–S4: кожна точка M, яку бачить лінза (промінь без перешкод, власні оболонки
машин виключено), лежить на висоті ≥ 4,0 м — рівні тераси.

Що зроблено в `tools/world/city_tidy_check.gd`:
- константа `STREET_SEEN_FLOOR = 4.0` — літерал A5 ([[2026-10-14-T6-Crane-Winch-Acceptance]] § 3 п. 1); допуск 1 мм на
  float. Виміряні мінімуми 4,30 / 4,45 / 4,30 — запас 0,3 м;
- у `_mc_street_camera()` на кожній станції: `_check(seen == 0 or seen_low >= 4.0 − 0.001, "MC7 <S> …: the lens sees no
  machine point under the terrace's level 4.0 m (lowest seen …)")`; рядок `CITY_TIDY_INFO MC7 … in_frame … seen … seen_y`
  друкується, як і раніше;
- три негативи `MACHINE_BREAKS`, по одній формі зламу;
- `tools/gates/playable_check.sh` — лише додані рядки (`git diff tools/gates/playable_check.sh | grep -c "^-[^-]"` → 0):
  три кейси `city-tidy-negative-machine_seen_*`, очікуваний rc 1.

| форма | що робить | що впало (з логу) |
|---|---|---|
| `machine_seen_hook` | декор крана, що стоїть на своєму місці: брусок 0,3 × 0,8 × 0,3 м (ще одна поверхня його ж меша, його ж матеріал) висить на (29,3; 2,6–3,4; −8,8) над вулицею | **3 × новий гард** (найнижче 2,60 м на S2, S3, S4) + MC3 «sinks 1.400 m» (низ бокса меша) — `failures=4` |

У `t2d-tree`, `GODOT_BIN=scratchpad/tools/godot-4.7/Godot_v4.7-stable_linux.x86_64` (`4.7.stable.official.5b4e0cb0f`), логи `B3/logs/`:
- `make check` (`make_check_final.log`) → rc 0: GDS `перевірено: 144 · не парсяться: 0 · не виміряно: 0 · канарка: FAIL
  як треба`; `[smoke] ALL OK (165 checks) in 19847 frames`, `SMOKE ЗЕЛЕНИЙ`;
- `make gates` (`make_gates_final.log`, після останньої правки цієї сторінки) → rc 0, `БАТАРЕЯ ЗЕЛЕНА`: ВІК `сторінок: 537 · … · зламаних: 0`; РЕЄ `187 · у реєстрі:
  187 · незареєстрованих: 0`; ПАР `проблем: 0`; GDS `перевірено: 144 · не парсяться: 0` (GDS-гейт бачить лише `game/**/*.gd`,
  тому `tools/` — окремо, рядок нижче);
- інструменти поза GDS-гейтом: `godot --headless --path game --check-only --script tools/art/albedo_ab_capture.gd` → rc 0,
  рядків помилок 0; те саме для `tools/world/city_tidy_check.gd` → rc 0, 0;

## Що лишилось відкритим

1. **M3 не бачено.** Кадри — Compatibility / llvmpipe; тінь Б3 у них світліша й сіріша, ніж дає формула Forward+.
   Інструмент без `--rendering-method gl_compatibility` мав би працювати й на M3 — так не запускався.
2. **Ціль тіні — моє прочитання задачі.** «Тінь у палітрі» дослівно (тінь = hex) вироджена — без тіні; я взяв правило
   стайл-гайду (hex × `#B07AA6`). Якщо T1 / Santos мали на увазі інше (наприклад, зберегти нинішню м'якшу частку тіні
   `mix(0.5, T, 0.35)`, лише вирівнявши світло), Б3 треба перерахувати — скрипт це робить за хвилину.
3. **Тінь темних ключів біля лінії** (чавун 9,2 проти мірила T6 ≥ 20) — художнє рішення T6.
4. **Колір tint у героїв** — синюватий типовий `(0.25, 0.3, 0.45)` на тілі й `RigAnimator`; стайл-гайд: «замінити у фазі
   2». Б3 міняє лише силу, тому тінь тіла не доходить до цілі (медіана 13,0).
5. **Лампи крамниць у `city_surface`** (вада з 2026-10-14) у Б3 помітніші в Compatibility.
6. **Розбіжність кадрів А / Б1 з моделлю Compatibility** (медіана 5–6; у Б3 0,4–0,5) — причину не з'ясовано.
7. Б3 — не правка продукту. Якщо Santos обере Б3, числа з таблиці «Нові числа» підуть у `city_surface.gdshader`,
   `CityInteriors.gd`, `CityBackdrop.gd` і шейдери героїв окремим кроком (Yellow, з ADR).
8. `state.md` і журнал зустрічі не правлю: рядок стану після зведення — T1. Не комічу, не пушу.
